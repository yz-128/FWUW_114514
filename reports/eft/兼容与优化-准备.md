## 一、"C 会不会影响打 jar？"——不会，已实测

| 检查 | 结果 |
| --- | --- |
| Gradle 打包范围 | `jar` 只收 `sourceSets.main`（`src/main/java` + `src/main/resources` + `src/generated/resources`），没有任何 source set 包含 `tools/` |
| `flansmod-0.5.11.jar` 内容 | 338 个条目，**0 个** `.exe/.dll/.so/.dylib`（`jar tf` 实测） |
| `flansmod-0.5.11-classic.jar` | 同样 0 个 native 文件 |
| 防回归 | `tools/native/build.ps1` 末尾自动跑"jar 内不得有 native 载荷"检查，泄漏即失败（本轮输出：`jar-clean: … has no native payload`） |

结论：C 只在**离线工具/参考实现**层（用户已定范围），构建发布链路保持纯 Java。

## 三、第一个离线工具：`pngstat`

```text
pngstat <image.png> [--region x y w h] [--diff other.png [--threshold N] [--out-diff f.png]] [--top-colors N]
```

用途：GPU 审计证据的**区域统计 / 差分 / 差异热图**，替代"启动 JVM 数像素"。

本轮实测（0.5.9 的 G33 证据）：

```
$ pngstat G33Enabled-yaw+25-pitch+10-production.png \
         --diff ...-native-depth.png --threshold 2 --out-diff build\g33-prod-vs-depth.png
diff 1280x720  pixels=921600
  changed(>2)=0 (0.000%)  mean delta=0.000  max delta=0
```

→ 0.5.9 的"生产管线"与"独立深度参考"逐像素**完全一致**（0 差异），这是之前那轮报告的定量复核。

中央区域统计（240×180 @ 560,240）也给得出可量化数字：G33 区域 13 种颜色、纯黑占 32.04%；ELCAN 对照 10 种、纯黑 21.94%——后续 GPT 定位灰块时可以直接用它筛"哪种灰"。

## 四、渲染仪表化（0.5.11，默认零开销）

| 类 | 作用 | 开关 |
| --- | --- | --- |
| `client/render/RenderPerf` | 统计 ADS 镜内相机单帧耗时、每帧 rig 四边形数、帧率窗口；每 1200 帧打一行 `[RenderPerf]` | `-Dflansmod.renderPerf=true` |
| `client/CompatReport` | 首帧打一行 `[Compat]`：加载的优化/光影模组、Iris 开/关/阴影 pass、Fabulous、镜内双相机是否可用、GL version/vendor/renderer | 始终（一行日志） |
| `tools/offline/VerifyRenderPrep` | 19 条离线断言：开关存在、关闭时零记录、两处热路径钩子、兼容报告字段 | 每次审计 |

钩子位置（均 `ENABLED` 守卫，正常玩家零开销）：
- `ScopeWorldTexture.begin` → `RenderPerf.frame()`
- `ScopeWorldTexture.prepare` → 独立相机 pass 计时
- `RigRenderer.render/renderPart` → 四边形计数

**测量协议**：dev 客户端加 `-Dflansmod.renderPerf=true`，进游戏 ADS 20 秒，读 `run/logs/latest.log` 的 `[RenderPerf]` 行；同时读首帧 `[Compat]` 记录环境。优化前后都在同一环境、同一倍镜、同一张图对比。
